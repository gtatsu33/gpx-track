■3. Supabase
3.1 事前設定（ユーザーがダッシュボードで行う）
 1. プロジェクトを作り、Project URL と Publishable key（sb_publishable_...）を控える
 2. Authentication > Providers で Anonymous Sign-Ins を有効にする
 3. Realtime > Settings で「Allow public access」を無効にする（private チャネルを必須にするため）
 4. SQL Editor で supabase/schema.sql を実行する。続けて set_owner_passcode.sql のパスコードを書き換えて実行する

3.2 テーブル（public スキーマ。すべて RLS を有効にする）
- profiles
  - id uuid PK（auth.users.id）、name text（1〜20文字）、updated_at
- app_config
  - id int PK（常に1）、owner_passcode_hash text
  - ポリシーを付けないので、クライアントからは読めない
- rooms
  - id uuid PK、code text unique（6文字）、team_name text、owner_id uuid
  - duration_min int null、min_lap_sec int default 30、moving_kmh int default 15（3〜100）
  - line_a_lat, line_a_lng, line_b_lat, line_b_lng（double precision、null可）
  - status text：'ready' / 'running' / 'finished'
  - mode text default 'team'：'team'（団体戦） / 'solo'（個人戦）（v2.0.0 で追加。既存のルームは団体戦）
  - started_at, finished_at（timestamptz、null可）
  - owner_id uuid（ルームを作った端末。v1.1.0 からは権限の判定に使わない）
  - owner_rider_id uuid null（オーナーのライダー。今のライダーがこれになっている端末がオーナーモード）
  - last_crosser_id uuid null（最後に通過した端末。地図で強調する端末の代わりに使う）
  - last_crosser_rider_id uuid null（最後に通過したライダー。現在のライダーの代わりに表示する）
  - created_at
- riders（名簿。v1.1.0 で追加）
  - id uuid PK、room_id、name text（1〜20文字）、user_id uuid null、created_at
  - unique(room_id, name)
  - user_id：参加したときに自動で作った「本人のライダー」なら、その端末のユーザー。名簿から追加した人は null
- room_members（端末）
  - room_id、user_id、color_idx int、joined_at、PK(room_id, user_id)
  - current_rider_id uuid null（この端末の今のライダー）
  - spectator bool default false（走らない端末（観戦・運営）。v2.0.0 で追加）
- crossings（通過の記録）
  - id uuid PK、room_id、crosser_id（ラインを越えた端末）、crosser_name text（その時点のライダーの名前）
  - rider_id uuid null（通過したときの端末のライダー）
  - crossed_at timestamptz、source text：'gps' / 'manual'
  - driver_override_rider_id uuid null（オーナーが修正したライダー）
  - driver_override_id uuid null（v1.0.x の名残。使わない）
  - deleted bool default false、created_at
  - 部分ユニークインデックス (room_id, rider_id, crossed_at) where not deleted
    - v2.0.0 で (room_id, crossed_at) から変更。個人戦で別の人がほぼ同時に越えても両方記録するため
    - 団体戦の「同時に越えたら片方だけ」は、record_crossing のロックと最小ラップ秒数の確認、add_manual_crossing の同じ時刻の確認で守る
- distance_segments（走行距離の記録）
  - id bigserial PK、room_id、user_id、rider_id、t_from timestamptz、t_to timestamptz、meters real
  - index (room_id, t_to)
  - BEFORE INSERT トリガーで、rider_id が null かルームのライダーでなければ、その端末の今のライダーを入れる
- messages
  - id bigserial PK、room_id、user_id null、name text、body text（1〜50文字）
  - kind text：'user' / 'system'、created_at

3.3 RLS
- メンバーかどうかの判定には is_room_member(room uuid) を使う（security definer、stable）。RLS が再帰しないようにするため
- SELECT
  - rooms / room_members / riders / crossings / messages / distance_segments は、is_room_member(room_id) のときだけ読める
  - profiles は、本人と、同じルームのメンバーの行だけ読める
- INSERT
  - messages：user_id = auth.uid()、kind = 'user'、メンバーであること
  - distance_segments：user_id = auth.uid()、メンバーであること、レース中であること
  - profiles：本人の行だけ upsert できる
- DELETE
  - room_members：本人の行だけ削除できる（ルームからの退出に使う）
- messages の name は、BEFORE INSERT トリガーでその端末の今のライダーの名前（なければプロフィールの名前）に置き換える（なりすまし防止）
- それ以外の書き込みはすべて RPC を通す。RPC は security definer にし、関数の中で権限を確認し、search_path = '' に固定する

3.4 RPC
- create_room(passcode, team_name, duration_min, min_lap_sec, moving_kmh, mode = 'team')
  - v1.x の5引数版は drop function で削除する
  - extensions.crypt でパスコードを照合する。紛らわしい文字を除いた6文字のコードを作り、重複したら作り直す
  - ルームと、作った人の本人のライダーを作り、それを owner_rider_id にする。メンバー行の current_rider_id にも入れる
- join_room(code)
  - メンバーに追加する（参加済みなら何もしない）。color_idx は参加順に割り当てる
  - 個人戦で、参加済みでない端末が上限（_solo_max_members() = 15）に達していれば 'room_full'
  - current_rider_id が null なら、本人のライダーを割り当てる（_assign_own_rider）
    - 優先順：その端末の本人のライダー → プロフィールと同じ名前のライダー → 新しく作る（同じ名前があれば末尾に数字）
    - オーナーのライダーはパスコードが必要なので、ここでは選ばない
- reclaim_owner(code, passcode)
  - パスコードが一致したら join_room してから、current_rider_id を owner_rider_id にする
- switch_rider(room, rider, passcode = null)　［メンバー］
  - rider がルームの名簿にあることを確認する（なければ 'not_rider'）
  - rider が owner_rider_id なら、パスコードを照合する（_check_passcode）
  - current_rider_id を rider にする
- add_rider(room, name)　［メンバー］
  - 名簿に追加し（user_id = null）、current_rider_id にする。同じ名前があれば 'duplicate_name'
- rename_rider(room, name)　［メンバー］
  - この端末の今のライダーの名前を変える。同じ名前がほかにあれば 'duplicate_name'
- set_room_mode(room, mode)　［オーナー］
  - スタート前（status = 'ready'）だけ。'team' / 'solo' 以外は 'invalid_mode'
- set_spectator(room, on)　［メンバー］
  - この端末の room_members.spectator を変える（走らない端末にする／戻す）
- ［オーナー］の確認（_require_owner）：呼び出した端末の current_rider_id が rooms.owner_rider_id と一致すること
- set_line(room, a_lat, a_lng, b_lat, b_lng)　［オーナー］
- update_room_settings(room, min_lap_sec, moving_kmh)　［オーナー］
- start_race(room) / set_start_time(room, ts) / finish_race(room)　［オーナー］
  - 状態と時刻を更新し、システムメッセージを投稿する
- record_crossing(room, crossed_at, rider = null)　［メンバー］
  - rider：通過した瞬間のその端末のライダー（再送で遅れて届くことがあるため端末から送る）。null かルームのライダーでなければ、その端末の今のライダーにする
  - v1.0.x の2引数版は drop function で削除する（引数の数が違う関数が並ぶと、呼び出しがあいまいになるため）
  - rooms の行を FOR UPDATE でロックしてから直前の通過を確認する（ほぼ同時に2人が通過したときの競合を防ぐため）
  - 確認する条件：spec 5.2 に加えて、now() より5秒以上未来の時刻は拒否する
  - 走らない端末からは 'spectator' を返して記録しない
  - 最小ラップ秒数は、前後の通過（再送で古い時刻が届く場合があるため前後両方）とレース開始時刻のどちらからも離れていることを確認する
    （スタート直後にラインを越えても1周と数えないため）
    - 団体戦はチームのすべての通過と、個人戦は本人（coalesce(driver_override_rider_id, rider_id) = rider）の通過と比べる
  - 個人戦でライダーが決まらない（null）ときは 'no_rider' を返して記録しない
  - 同じ人が同じ時刻で送ってきた場合は 'duplicate' を返す（再送のため）
  - 記録したら rooms.last_crosser_id と last_crosser_rider_id を更新する（値が変わるときだけ）。団体戦で、前の通過と違うライダーなら「ライダー交代：◯◯」のシステムメッセージを投稿する
  - 戻り値：'recorded' / 'duplicate' / 'too_soon' / 'not_running' / 'out_of_range' / 'spectator' / 'no_rider'
- add_manual_crossing(room, crossed_at, rider = null)　［オーナー］
  - v1.x の2引数版は drop function で削除する
  - source = 'manual'。最小ラップ秒数は確認しない
  - 団体戦：crosser と rider には、その時刻の直前の通過の端末とライダー（いなければ last_crosser_id / last_crosser_rider_id、それもなければ呼び出した端末 / オーナーのライダー）を入れる。rider 引数は使わない。同じ時刻の通過があれば 'duplicate_time'
  - 個人戦：rider は必須（名簿になければ 'not_rider'）。crosser は呼び出した端末。同じ人の同じ時刻の通過があれば 'duplicate_time'
- delete_crossing(id)　［オーナー］
  - deleted = true にする（論理削除）
- set_crossing_driver(id, rider or null)　［オーナー］
  - driver_override_rider_id を設定する。null なら自動判定に戻す
  - 引数名を p_user から p_rider に変えたため、drop function してから作り直す
- get_lap_table(room, from = 1)　［メンバー］
  - ラップ表を返す（3.5を参照）。通し番号が from 以降の行だけを返す（通信量を抑えるため。省略すると全周）
  - v1.2.0 までの1引数版と、v2.0.0 で戻り値の列（rider_lap_no）を足す前の版は drop function で削除する
- update_profile_name(name)　［本人］

3.5 ラップ表の計算（get_lap_table。サーバー側で計算する）
- 対象は deleted = false の crossings。crossed_at の昇順に並べ、row_number() を通し番号（lap_no）にする（両方のモード）
- 周の区間
  - 団体戦：[チームの前の通過時刻, 今回の通過時刻]。1周目は [started_at, 1回目の通過時刻]
  - 個人戦：[本人の前の通過時刻, 今回の通過時刻]。本人＝coalesce(driver_override_rider_id, rider_id)。1周目は started_at から
- 個人戦では本人の周番号 rider_lap_no も返す（row_number() over (partition by 本人 order by crossed_at)）。団体戦では null
- 個人戦は走行距離を集計せず、ラップのライダーは本人にする（driver_meters は null）
- 以下の走行距離とライダーの決め方は団体戦だけ
- ライダーごとのその周の走行距離＝区間と重なる distance_segments の meters を rider_id ごとに合計する
  - 一部だけ重なる区間は、重なった時間の割合で按分する
    - meters × (least(t_to, 周の終わり) − greatest(t_from, 周の始まり)) / (t_to − t_from)
- ラップのライダーを決める優先順位
  1. driver_override_rider_id
  2. 走行距離が最も長いライダー（同じなら通過したライダー rider_id）
  3. どちらもなければ通過したライダー rider_id
- 名前は riders の今の名前を使う（取れなければ crosser_name）
- 戻り値の列：lap_no（通し番号）, crossing_id, crossed_at, lap_ms, driver_id（ライダーID）, driver_name, driver_meters, source, is_override, crosser_id（端末）, rider_lap_no（個人戦の本人の周番号）
- from を指定したとき：周番号とラップタイムを正しく付けるため、通過の並べ替えは全周で行う。走行距離の集計と返す行は from 周目以降だけにする
- 名前の確定：直近の周で、終わってから15秒未満のものは「暫定」とし、クライアント側で薄く表示する

3.5.1 v1.0.x からの移行（schema.sql の最後の DO ブロック。まだ移していない行だけが対象なので、何度実行してもよい）
- オーナーの端末に本人のライダーを作り、owner_rider_id にする
- ほかのメンバーにも本人のライダーを割り当てる（_assign_own_rider）
- crossings.rider_id / driver_override_rider_id、distance_segments.rider_id に、その端末の本人のライダーを入れる
- last_crosser_rider_id を取り直す

3.5.2 ラップ表の取り直し（hooks/useRoom.ts、lib/laps.ts）
- 「全部」と「後ろだけ」の2通りで取る
  - 後ろだけ：手元の最後の周を from にして取る（1行重ねる）。重ねた周の crossing_id が手元と違えば、途中で周番号がずれたとみなして全部を取り直す
- どちらで取るか
  - 後ろだけ：最後に追加された通過の配信（op = 'insert' で、手元の最後の周より後の時刻）、その16秒後の確定（団体戦だけ）、自分の通過の記録、1分ごとの定期取得
  - 個人戦も通し番号で取るので、同じ仕組みが使える
  - 全部：それ以外の通過の配信（削除・名前の修正・過去の時刻への追加）、開始時刻の修正（id が null の配信）、ルームを開いたとき・再接続したとき、オーナー操作のあと、10回に1回の定期取得（10分ごと）
- 取得は1本ずつ順番に行う。取得中に来た依頼は1つにまとめて、終わったあとに行う（全部 > 後ろだけ の優先）。応答が前後して古いデータで上書きしないため
- ベスト、平均、★、暫定の表示は、差し替えたあとのラップ表全体から計算する
- 結果の出力（ExportMenu）は、毎回全部を取る

3.6 Realtime
- 1ルームにつき private チャネルを1本だけ使う
  - トピック：room:<room_id>
  - 設定：{ private: true, broadcast: { self: false }, presence: { key: user_id } }
- realtime.messages に付けるポリシー（SELECT と INSERT、対象は authenticated）
  - exists(select 1 from public.room_members m where m.user_id = (select auth.uid()) and 'room:' || m.room_id::text = (select realtime.topic())) and realtime.messages.extension in ('broadcast','presence')
  - realtime.messages には ALTER TABLE をかけない（公式ドキュメントで禁止されているため）
- クライアントから送る broadcast「pos」：{ uid, rid, lat, lng, acc, spd, moving, t }（rid はその端末の今のライダー）
- presence：参加したときに track({ uid, name }) を1回だけ行う（Presence は頻繁に更新しない、という公式の注意に従う）
- DBの変更の配信：rooms / crossings / messages / room_members / profiles（名前の変更）/ riders（名簿の追加と名前の変更。member イベント）に AFTER トリガーを付ける
  - realtime.send(payload, event, 'room:' || room_id, true) で同じトピックに送る
  - 配信に失敗しても本来の処理（通過の記録など）は止めない（例外を握りつぶして警告だけ出す）
  - イベント名：room / crossing / message / member
  - crossing の payload：{ id, op（'insert' / 'update'）, crossed_at }。開始時刻の修正のときは { id: null }
  - distance_segments の挿入は配信しない（配信の回数を節約するため）
  - postgres_changes は使わない（DELETE で絞り込めないこと、private チャネル1本にまとめられないことが理由）
- 受け取ったときの処理
  - message：リストに追加する
  - crossing：get_lap_table を呼び直す（全部か後ろだけかは 3.5.2）。団体戦では、さらに16秒後に後ろだけをもう一度取り、遅れて届いた距離データで名前を確定させる（個人戦はライダーが通過で決まるので不要）
  - room / member：該当するデータを取り直す
- チャネルの状態が SUBSCRIBED に戻ったとき（再接続したとき）は、すべてのデータを取り直して取りこぼしを埋める
- サインインした後に supabase.realtime.setAuth() を呼んでからチャネルに参加する（今のSDKで必要かどうかは実装するときに確認する）

3.7 無料枠の見積もり（2026-11 時点の Supabase 料金ページで確認）
- 無料枠
  - Realtime メッセージ 200万/月、同時接続 200、毎秒 100メッセージ
  - DB 500MB、月間アクティブユーザー 5万
  - 1週間使わないと一時停止する
- 数え方：Broadcast は「送信1回＋受信する人数分」、DBからの配信は「受信する人数分」
- 位置の配信（v2.0.0：ピットの人は送らない）
  - 団体戦（走行中の1人が0.2回/秒（5秒ごと））
    - 5人：0.2×(1＋4)＝1メッセージ/秒 → 7時間で約2.5万
    - 10人：0.2×(1＋9)＝2メッセージ/秒 → 7時間で約5万
  - 個人戦（全員が走行中で0.1回/秒（10秒ごと））：n人なら 0.1×n×n メッセージ/秒
    - 10人：10メッセージ/秒 → 7時間で約25万
    - 15人（上限）：22.5メッセージ/秒 → 7時間で約57万（毎秒100の上限には収まる）
- ラップとチャットの配信は1レースで数千メッセージ程度なので、ほぼ影響しない
- 走行距離は REST での INSERT なので、Realtime メッセージには数えられない（団体戦だけ）
  - 7時間で約2,500行（10秒ごと×1人）。DB容量への影響もほぼない
- 結論：7時間レースなら、団体戦は5人で月70回程度、10人で月35回程度。個人戦は10人で月8回程度、15人で月3回程度まで無料枠に収まる
- 無料枠を超えても課金はされない（通知が来て猶予期間に入る）
- Cloudflare Workers：静的アセットへのリクエストは、無料プランでも無料・回数無制限

■4. 通過判定（lib/lapDetector.ts）
- 入力：直前の測位P、今回の測位Q、ラインの端点A・B、設定（延長15m、最大間隔20秒、判定速度）
- 平面化：ラインの中点 (lat0, lng0) を原点にした正距円筒近似を使う
  - x = Δlng × cos(lat0) × R、y = Δlat × R（R = 6371008.8m、角度はラジアン）
- AB を両端15mずつ延長して A'B' とし、d = B'−A'、r = Q−P とする
  - den = cross(r, d)。den = 0（平行）なら交差しないとする
  - t = cross(A'−P, d) / den、u = cross(A'−P, r) / den
  - 0 ≤ t ≤ 1 かつ 0 ≤ u ≤ 1 なら交差する
- 速度の条件：|Q−P| / (Q.t−P.t) が判定速度（m/sに換算）より遅ければ、通過にしない
- 時間の条件：Q.t − P.t が20秒を超えていたら判定しない
- 通過時刻：P.t + t × (Q.t − P.t)（時刻は position.timestamp を使う）
- 同じ端末で、前回の通過から最小ラップ秒数たっていない場合は送信しない（サーバー側でも確認する）

■5. 走行状態と走行距離（lib/movingState.ts）
- 精度が30mより悪い点は捨てる（直前の点も更新しない）
- 速度：coords.speed（m/s）が null でなければそれを使う。null なら直前の点との距離÷時間で求める
- 走行状態の切り替え（ヒステリシスで状態がちらつくのを防ぐ）
  - ピット→走行中：判定速度以上が10秒続いたとき
  - 走行中→ピット：判定速度未満が30秒続いたとき
- 走行距離：直前の点から今回の点までの区間速度が判定速度以上で、間隔が20秒以内なら、その距離を加える
- 加えた距離は10秒ごとに1つのセグメント { t_from, t_to, meters } にまとめて、その端末の今のライダー（rider_id）を付けて distance_segments に INSERT する（団体戦だけ。個人戦では送らない）
  - この端末のライダーを切り替えたときは、それまでの距離を前のライダーの分として先に送る
  - meters が 0 のセグメントは送らない
  - 送信に失敗したら crossingQueue に入れて再送する
  - レース中のときだけ送る

■5.1 位置の送信と走らない端末（hooks/useTracker.ts、lib/posPolicy.ts）
- 位置を送るかどうか（shouldSendPos）
  - まだ1回も送っていなければ送る（ピットでも。地図に最初の位置を出すため）
  - 走行中：前回から送信間隔（団体戦 POS_INTERVAL_MOVING_MS、個人戦 POS_INTERVAL_MOVING_SOLO_MS）たったら送る
  - ピット：前回送ったのが走行中の位置なら1回だけ送り（ピットになったとき）、あとは送らない
  - 送らないときも、自分の地図の表示は更新する（setOwnPos）
- 走らない端末（room_members.spectator = true）
  - useGeolocation を止める（watchPosition を呼ばないので、位置情報の許可も求めない）。通過の判定と走行距離の計算も止まる
  - 走らない端末から戻ったときは、通過の判定器と送信の状態をリセットする

■6. ラップ表の表示（lib/laps.ts）
- get_lap_table の結果を降順に並べ替え、ベストラップ（lap_ms の最小値。手動の周も含む）、平均、★を付ける
- 暫定の周（3.5）は名前を薄い色で表示する

■7. フロントの実装メモ
- Leaflet
  - タイル URL：https://tile.openstreetmap.org/{z}/{x}/{y}.png、maxZoom 19
  - attribution：&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> contributors
  - OSM の利用規約に従い、先読みや一括ダウンロードはしない。Referrer-Policy は既定のまま（no-referrer にしない）
- マーカーは L.divIcon で作る（色付きの丸と名前）。パレットは10色で、color_idx を10で割った余りで選ぶ
  - 個人戦の名前ラベルは「名前 周回数」（lib/standings.ts の lapCountByRider でライダーごとに数える）
  - 走らない端末のマーカーは出さない
  - 強調する端末：団体戦は現在のライダーの端末、個人戦は自分（走らない端末なら強調しない）
- 個人戦の順位（lib/standings.ts の computeStandings）
  - get_lap_table の結果を driver_id（ライダー）ごとにまとめる。周回数の多い順、同じなら最後の通過が早い順
  - トップとの差：同じ周回数なら最後の通過の時刻の差、少なければ周回の差
  - 周回が0でも、走る端末で今のライダーになっている人は下に載せる（順位は付けない）
  - ヘッダー、順位タブ、マップのラベル、結果の出力で同じ関数を使う
- 現在のライダー：pos の moving が true の端末を選ぶ。複数いれば速度が速い方。名前はその pos の rid のライダー
  - 誰もいなければ、端末は rooms.last_crosser_id、名前は rooms.last_crosser_rider_id のライダー
- オーナーモードの判定（クライアント）：自分の room_members.current_rider_id が rooms.owner_rider_id と一致すること（サーバー側は _require_owner で確認する）
- Wake Lock
  - 'wakeLock' in navigator で対応しているか判定する
  - navigator.wakeLock.request('screen') を try/catch で囲む
  - visibilitychange で visible に戻ったら取り直す
- 時刻：表示は端末のローカル時刻。サーバーへは ISO8601（UTC）で送る
- alert と confirm は使わず、Modal コンポーネントで表示する
- 画面の切り替えは state で行う。URL は ?room=<code> だけ読み取り、参加の入力を補助する
- 結果の出力（components/ExportMenu.tsx、lib/export.ts）
  - 開いたときに rooms / get_lap_table / riders を取り直す。共有はボタンを押した直後に呼ぶ必要がある（ユーザー操作の中で呼ぶ）ため、データは先に取っておく
  - 集計は get_lap_table の結果からクライアントで行う（サーバーの変更なし）。ベストと平均は lib/laps.ts の buildLapView と同じ値を使う
  - CSV：Blob(['﻿', 本文], { type: 'text/csv;charset=utf-8' })
    - iOS / iPadOS（UA が iPhone/iPad/iPod、または Macintosh でタッチ対応）で navigator.canShare({ files }) が true なら navigator.share({ files }) を使う
      （iOS Safari 14 以降で files の共有に対応。古い iOS で canShare が false になる報告があるので必ず確認する）
    - それ以外と、共有に失敗したとき（AbortError を除く）は、URL.createObjectURL と <a download> でダウンロードする
  - 共有テキスト：navigator.share({ text }) → navigator.clipboard.writeText → テキスト欄に表示、の順に試す。AbortError（ユーザーが閉じた）は何もしない
- 認証（hooks/useAuth.ts）：削除されたユーザーからの自動復帰（@supabase/auth-js 2.118.0 のソースで動作を確認）
  - 名前を登録・変更したら localStorage の gpx-track.name にも保存する
  - 起動時、getSession() でログイン情報があれば getUser() でサーバーに確認する
  - エラーが AuthSessionMissingError、または AuthApiError で code が user_not_found / session_not_found か status が 401 / 403 / 404 なら、ユーザーが消されたと判断する
    - 通信エラー（AuthRetryableFetchError、status 0）は対象にしない
  - そのときは signOut({ scope: 'local' }) で端末のログイン情報だけを消す（このSDKは 401 / 403 / 404 を無視して端末の情報を消す）
    - あわせて localStorage の gpx-track.currentRoom と gpx-track.queue を消す
  - gpx-track.name があれば、signInAnonymously と update_profile_name で入り直す。App はルーム画面を開かずにホームを表示する
  - 名前の登録で外部キー違反（23503）が出たときも、同じようにログイン情報を消して1回だけ入り直す

■10. テストと確認
- 単体テスト（vitest）
  - geo：距離、平面化
  - lapDetector：交差する、しない、平行、延長した部分での交差、通過時刻の補間、速度が足りない、間隔が長すぎる
  - movingState：ヒステリシス、精度による除外、距離の加算、セグメントへのまとめ方
  - laps：降順の並べ替え、ベストラップ、平均、後ろだけ取り直すときの差し替えと、ずれの検知、後ろだけでよいかの判定
  - export：CSV のエスケープ、ライダー別の集計、CSV の3つの表と CRLF、ファイル名、共有テキスト（結果と途中経過）
  - solo：個人戦の順位（同じ周回数の並び、0周の人、トップとの差）、マップ用の周回数、個人戦の CSV と共有テキスト、位置を送るかどうか
  - format：時刻とラップタイムの書式
- SQL の確認（Supabase の SQL Editor）
  - get_lap_table の按分とライダー判定を、テスト用のデータで確認する（Aが7割、Bが3割走った周がAになること）
  - 個人戦：ほぼ同時の通過が両方記録されること、本人基準のラップタイムと周番号、走らない端末の拒否、端末数の上限
  - 団体戦が今までどおり動くこと（同じ時刻の手動追加の拒否、チーム基準のラップタイム）
- 開発用の疑似GPS
  - ?sim=1：半径約300mの円を約60秒で1周する。円は中心をライン中点からライン方向に半径分ずらして置き、中点でラインを直角に横切るようにする（中点を中心にすると、ラインを横切らないため）
  - ?sim=1&speed=20：時速20kmで周回する
  - ?sim=pit：ラインの近くを歩く速度で動く
- 結合確認（PCでブラウザを2つ開く。別プロファイルにして、別々の匿名ユーザーにする）
  - 作成 → 参加 → ラインの設定 → レース開始
  - Aを ?sim=1 にして数周させ、ラップ表とチャットが両方のブラウザに同期することを確認する
  - 周の途中でAを ?sim=pit、Bを ?sim=1 に切り替える
    - 「ライダー交代」が表示されること
    - その周の名前が、走った距離の長い方になること
    - ピットにいる人はカウントされないこと
  - 名前の修正（自動に戻すことも含む）、削除、手動追加、再接続したあとの取り直しを確認する
  - 個人戦：AとBを両方 ?sim=1 にして、順位タブ、ヘッダーの順位とトップとの差、マップの「名前 周回数」を確認する
  - 走らない端末：オンにすると位置が送られず、マーカーが消えること。ピットに入ると位置の送信が止まり、最後の位置がグレーで残ること
- 実機確認：workers.dev にデプロイし、スマホ2台で位置の表示と Wake Lock を確認する
